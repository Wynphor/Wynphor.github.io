AI 编程的进化：从提示词到可执行工作流

发表于2026-04-18|更新于2026-09-19|技术
|总字数:5.2k|阅读时长:15分钟|浏览量:

前言

兑现之前的约定，我用AI写了一篇如何使用AI的文章\\x7e\x7e(听起来有点怪)\x7e\x7e

本文由 ChatGPT-5.4 赞助写出（bushi）

如果说上一阶段的 AI 编程是在比“谁更会写代码”，那么这一阶段更像是在比“谁更不容易把事情搞砸”。

导读

过去一段时间，很多人把 AI 编程理解为三件事：

  • 写 Prompt
  • 让模型生成代码
  • 把结果复制回编辑器继续改

这种理解不能说全错，只能说停留在“试玩版认知”。今天更有价值的 AI 编程工具，往往不只是“会回答”，而是能够：

  1. 读懂代码库
  2. 接入工具链
  3. 在边界内执行任务
  4. 根据反馈继续修正
  5. 把结果交还给人审核

换句话说，AI 编程已经开始从语言交互走向工程执行。这也是为什么现在讨论 AI 编程，不能只盯着模型参数表像看彩票开奖一样激动，还必须看上下文、工具、工作流，以及外层的 harness。

一、为什么“AI 编程”正在被重新定义

最早一批 AI 编程产品的核心卖点，主要集中在以下能力：

  • 代码补全
  • 函数生成
  • 报错解释
  • 样板代码输出

这些能力当然有价值。它们显著降低了很多日常开发动作的摩擦，也让 AI 第一次真正进入开发者的主工作流。问题在于，有些人因此迅速得出结论：“程序员快下岗了。”这种判断通常和“看了两条健身视频就开始指导别人增肌”属于同一门学问。

但问题也很快暴露出来：

  • 它能写一个函数，不代表它能理解一个模块
  • 它能解释一条报错，不代表它能定位一个真实 bug
  • 它能给出一个修改建议，不代表它能跑验证并继续修复

也就是说，“生成代码”不等于“完成任务”。能把一段代码写出来，和能把一个问题解决掉，中间隔着一整套工程现实，不是多加两个提示词就能抹平的。

当任务从“写一段代码”升级为“在真实仓库中解决问题”时，事情就变了。此时一个工具是否好用，取决于它能不能处理下面这些问题：

  • 它能否拿到正确上下文
  • 它能否连接真实环境
  • 它能否执行工具调用
  • 它能否进入验证循环
  • 它能否在关键节点停下来让人审查

这就是今天 AI 编程被重新定义的原因。用户真正需要的，已经不是一个“更会吐代码”的模型，而是一个能参与真实研发流程的执行系统。说得不那么客气一点，老板买的也不是“会背八股文的赛博实习生”，而是能把活干完的工具。

二、我们应该用什么标准判断 AI 编程是否在发展

如果只看模型参数规模、基准测试分数，或者单次生成质量，很容易得出一种很昂贵的误判。对于开发者和团队来说，更实用的判断标准至少有五个。

1. 任务粒度是否扩大

一个只能处理代码片段的工具，和一个能处理跨文件、跨模块、跨步骤任务的工具，代表的不是同一代能力。

例如：

  • 低粒度任务：写一个排序函数
  • 中粒度任务：重构某个组件的状态逻辑
  • 高粒度任务：定位一个线上 bug，修复后补测试，再生成提交说明

2. 上下文能力是否增强

工具是否真正理解：

  • 仓库结构
  • 文档规范
  • 历史改动
  • 错误日志
  • 团队约束

这比“它是不是会写一段更漂亮的代码”更重要。因为在编程场景里，Prompt 决定表达方式，上下文决定理解上限。不会有人因为实习生句子写得漂亮，就把生产事故交给他负责；AI 也一样。

3. 环境连接能力是否提升

AI 是只能“提建议”，还是能：

  • 搜代码
  • 读文件
  • 跑命令
  • 查文档
  • 调外部系统

这会直接决定它处在“助手”还是“执行者”的位置。

4. 闭环能力是否形成

好的 AI 编程工具，不应该只输出一个看起来像答案的东西，还应该能够形成任务闭环：

  1. 理解问题
  2. 制定步骤
  3. 执行操作
  4. 验证结果
  5. 修正路径

5. 工程可靠性是否提高

一个能进入真实团队流程的工具，通常还要具备这些特征：

  • 权限边界明确
  • 审查点清晰
  • 输出可重复
  • 流程可复用
  • 结果可审计

对真实研发而言，最有价值的从来不是“偶尔特别聪明”，而是“经常稳定可用”。前者适合做演示，后者才能进流程。

三、理解 AI 编程的发展，为什么需要双视角

如果只从“大模型越来越强”来理解 AI 编程，会漏掉大量真实世界的问题。更准确的做法，是同时从两条视角来看：

  • 大模型视角：模型本身的推理、编码、长上下文和多步规划能力如何增强
  • Harness 视角：围绕模型构建的执行框架，如何组织上下文、路由工具、管理状态、做验证和权限控制

这两条视角回答的是不同问题：

  • 大模型路线回答：AI 自身变强了什么
  • Harness 路线回答：我们怎样让 AI 在真实研发环境中稳定工作

这也是今天很多工具“模型看起来差不多，体验却差很多”的根本原因。模型名片可以印得差不多，工程功底可没法靠海报补齐。

四、视角一：从大模型能力出发，AI 编程如何演进

4.1 Prompt Engineering：先解决“怎么问”

最早的阶段，重点是如何通过更清晰的指令，让模型生成更接近预期的结果。

这一阶段的典型收益包括：

  • 降低沟通歧义
  • 提高单次输出质量
  • 快速完成局部、静态任务

典型场景也很熟悉：

  • 写一个函数
  • 改一段 SQL
  • 解释一条报错
  • 生成一段样板代码

但 Prompt Engineering 很快会碰到边界。它的问题不是没用，而是只解决了“问法”问题，没有解决“环境”问题。很多人把提示词写得像古代奏折，结果依然改不对文件，原因并不神秘：模型根本不知道项目里发生了什么。

4.2 Context Engineering：再解决“给什么上下文”

当任务开始变复杂，问题就不再是“如何写一句更好的 Prompt”，而是“如何把正确的信息交给模型”。把上下文喂错，再强的模型也只能认真胡说。

对于编程工具来说，有价值的上下文通常包括：

  • 仓库目录结构
  • 目标文件与关联文件
  • 技术栈约束
  • 代码规范
  • 报错日志
  • 历史改动

工具一旦开始自动处理这些信息，体验会出现质变。很多时候，用户感受到的“这个工具更聪明了”，其实是这个工具更会组织上下文了。

4.3 Tool Use：从“会说”走向“会做”

下一步是工具调用。模型不只会解释问题，还能借助外部能力接触真实环境。

常见的工具能力包括：

  • 文件读取
  • 代码搜索
  • 终端命令
  • 文档查询
  • 平台接口调用

这一步的意义非常大，因为：

  • 没有工具，模型只能推测
  • 有了工具，模型才能验证

对于编程场景来说，这就是从“内容生成工具”走向“任务执行工具”的分水岭。

4.4 Agentic 执行：从一次回答走向多步推进

再进一步，模型开始具备多步执行能力。它不再是给出一个答案就结束，而是能够：

  1. 理解任务
  2. 拆分步骤
  3. 调用工具
  4. 根据反馈调整路径
  5. 汇报结果

这一阶段最容易让人兴奋，但也最容易产生误解。很多人会把 agent 理解成“尽量全自动”，仿佛只要把手离开键盘就算先进。但真正好用的 agent，通常不是无限自治，而是：

  • 边界明确
  • 工具可控
  • 状态可见
  • 关键节点可审查

五、视角二：从 Harness Engineering 出发，AI 编程如何演进

如果从 harness 的角度看，同一段历史会呈现另一条更工程化的演进链路。这个视角没有那么性感，但通常更接近钱花到哪里、坑踩在哪里的现实。

5.1 Prompt 只是最小控制层

在最早阶段，外层系统几乎不存在。用户自己组织输入、自己判断输出、自己执行结果。此时模型再强，也更像一个高级问答器。

5.2 上下文编排成为产品能力

接下来，产品开始主动做几件事：

  • 自动索引代码
  • 自动引入相关文件
  • 自动关联文档和历史信息
  • 自动处理会话记忆

这一步看起来不如模型升级那么“酷”，但往往更影响真实体验。工程世界里，真正值钱的东西经常都不太适合做发布会主视觉。

5.3 工具编排成为外层框架

再往后，问题变成：

  • 什么时候该搜索
  • 什么时候该读文件
  • 什么时候该运行命令
  • 什么时候该中止高风险操作

此时一个工具是否好用，越来越取决于外层框架是否合理，而不是模型本身是否“会写代码”。

5.4 Harness Engineering 成为主战场

今天讨论 harness，本质上是在讨论围绕模型搭建的任务执行框架与控制系统。它通常包括：

  • 上下文组织
  • 工具路由
  • 状态管理
  • 验证与重试
  • 权限控制
  • 人工审查点
  • 评估与观测

很多用户会说：“为什么两个接入相似模型的工具，实际效果差这么多？”
答案往往就在这里：模型相近，不代表 harness 相近。 同样的发动机，装在拖拉机和赛车上，开起来当然不是一个物种。

六、当前“大模型派”与“Harness 派”的核心分歧

这两条视角进一步演化，就会形成今天业内常见的两种倾向。简单说，一派觉得“模型再强一点，万事皆可平”；另一派觉得“别做梦，先把流程搭对”。

6.1 分歧一：进步主要来自模型，还是来自系统

大模型派更相信：

  • 更强的推理能力会吸收很多外层问题
  • 更长上下文和更强规划能力会减少对复杂流程封装的依赖

Harness 派更相信：

  • 真实研发中的瓶颈，首先不是“模型会不会写”
  • 而是“它是否拿到了正确上下文、是否调用了正确工具、是否经过了正确验证”

6.2 分歧二：产品壁垒建在哪里

可以把这个分歧简化成一句话：

  • 一派强调智能密度
  • 一派强调系统密度

也就是说：

  • 大模型派认为壁垒主要在模型能力
  • Harness 派认为壁垒主要在任务编排、知识组织、工具接入、权限治理和工作流落地

6.3 分歧三：失败应该归因于哪里

当一个工具没有修好 bug 时，可以有两种完全不同的归因方式：

  • 归因给模型：推理不够强、规划不够稳、代码理解不够深
  • 归因给系统：没读全文件、没引入日志、没跑测试、没设置审查点

在真实生产里，第二类问题往往暴露得更早。因为模型能力不够，可能要到复杂场景才看出来；但系统没搭好，第一天上线就能给你表演。

6.4 我的判断

我的判断很明确：

  • 大模型决定能力上限
  • Harness 决定交付下限

所以真正有效的方向，不是二选一，而是：

强模型 + 强 harness

七、如何理解一款 AI 编程工具到底强在哪里

如果你要评估一款工具，不建议上来就问“它用了什么模型”，那和买车先问音响品牌差不多，不能说毫无意义，但通常没抓到重点。更应该沿着下面这条链路来看。

7.1 Prompt 层：任务接口是否清晰

重点看：

  • 是否容易描述目标
  • 是否容易约束边界
  • 是否支持结构化表达验收标准

7.2 Context 层：是否真的理解仓库

重点看：

  • 是否能读懂项目结构
  • 是否能自动关联相关文件
  • 是否能引入团队文档和约束

7.3 Tools 层：是否真的具备执行能力

重点看：

  • 是否支持代码搜索
  • 是否支持文件读取
  • 是否支持运行命令
  • 是否支持接外部系统

7.4 Skills 层：是否支持经验复用

重点看：

  • 能否沉淀高频任务套路
  • 能否复用常见场景流程

典型高频任务包括：

  • 修 CI
  • 处理 PR review
  • 补测试
  • 补文档

7.5 Agents 层：是否具备多步推进能力

重点看：

  • 会不会主动找信息
  • 会不会汇报中间状态
  • 会不会根据反馈调整路径

7.6 Workflows 层：是否能形成稳定闭环

最终更值得看的，往往不是单点能力，而是它能否把这些能力串成一个稳定流程。单点都能演，闭环才见功夫。

八、从实用角度看，AI 编程工具常见的三种形态

8.1 IDE 型工具

更适合：

  • 局部修改
  • 小步重构
  • 报错解释
  • 样板代码生成

优势：

  • 摩擦低
  • 上手快
  • 和日常编码贴得近

局限：

  • 对跨系统任务和复杂闭环支持有限

8.2 CLI 型工具

更适合：

  • 仓库级搜索
  • 批量改动
  • 跑测试
  • 看日志
  • 生成提交说明

优势：

  • 更贴近真实工程链路
  • 更适合任务闭环
  • 更适合自动化

局限：

  • 使用门槛高于 IDE

8.3 API / 平台型工具

更适合：

  • 接入内部研发平台
  • 嵌入代码评审流
  • 接入 CI / CD
  • 对接权限和审计系统

优势：

  • 可治理
  • 可审计
  • 可定制

局限：

  • 落地成本更高

简单概括：IDE 重体验，CLI 重执行，API 重集成。

九、对开发者最有价值的 5 类使用场景

从工具实用性出发，下面五类场景通常最容易稳定获得收益。它们有一个共同点：不是为了炫技，而是为了少走弯路、少返工、少熬夜。

9.1 快速理解陌生代码

建议让工具先做这些事：

  1. 总结目录结构
  2. 标出关键文件
  3. 解释模块职责
  4. 梳理调用关系

9.2 定位 bug 和回溯问题

更推荐的流程是：

  • 先给症状和日志
  • 再让工具定位链路
  • 最后再让它提出修改方案

而不是一上来就说“帮我修”。这种指令的工程含量，和对着医生说“你看着办”差不多。

9.3 小步重构和重复性修改

这类任务通常很适合 AI：

  • 改命名
  • 抽公共逻辑
  • 统一接口
  • 批量替换样板

关键是边界要清晰，避免改动蔓延。否则它本来只是来帮你整理房间，最后把承重墙也一起拆了。

9.4 补测试和补文档

这是非常适合 AI 发挥的场景，因为它们通常：

  • 输入结构清晰
  • 产出格式明确
  • 收益直接可见

9.5 处理 PR review 和 CI 问题

这是最接近完整任务闭环的一类场景。一个好用的工具应当能帮助你：

  1. 读取评论或失败日志
  2. 定位相关代码
  3. 修改实现
  4. 运行验证
  5. 汇总结果

十、比“会写 Prompt”更重要的 6 个使用原则

1. 先拆任务，再让工具执行

复杂目标不要一次性丢给工具。更好的方式是拆成：

  • 理解问题
  • 找相关文件
  • 改实现
  • 跑验证
  • 汇报结果

2. 给边界，不只给目标

至少说明这些内容：

  • 要改什么
  • 不要改什么
  • 风格要求
  • 验证方式
  • 输出格式

3. 先分析，再执行

推荐顺序：

  1. 先让工具总结问题
  2. 再让它给出方案
  3. 最后再执行改动

4. 强制进入验证循环

生成不代表完成。改完之后至少要：

  • 跑测试
  • 看日志
  • 对比结果
  • 必要时继续修正

5. 优先复用流程，而不是重复手工操作

可以沉淀的内容包括：

  • 常用 Prompt 模板
  • 常见任务清单
  • Skills
  • Workflows

6. 保留人工审查点

这些环节通常不应该直接放权：

  • 架构调整
  • 高风险权限操作
  • 安全相关改动
  • 最终合并

十一、个人和团队该如何选择 AI 编程工具

对个人开发者

优先看三件事：

  • 是否顺手
  • 是否理解本地代码
  • 是否覆盖你的高频任务

对小团队

重点看：

  • 是否支持共享规范
  • 是否便于沉淀流程
  • 是否能接入现有工具链

对平台团队和管理者

更应该看：

  • 权限边界
  • 审计能力
  • 集成能力
  • 评估机制
  • 可观测性

这里有一个非常实用的判断问题：

选 AI 编程工具时，不要先问“它模型多强”，而应先问“它能否稳定完成我的高频任务”。前者适合做社交媒体讨论，后者才影响你的周报。

十二、对计算机从业者的建议

AI 编程对从业者的真正影响，不只是“写代码更快”。更准确地说，它会把“谁负责写”和“谁负责判断”这两件事拉得更开。

更现实的变化是：

  • 初级重复劳动会更快被自动化
  • 中高级岗位会更强调架构判断、流程设计和质量控制
  • 个人能力会从“手工完成任务”转向“设计可复用流程”

因此，值得强化的能力包括：

  • 任务拆解
  • 上下文组织
  • 输出验收
  • 风险识别
  • 系统设计
  • 调试能力
  • 测试意识
  • 安全意识

一个很重要的结论是：

AI 降低了部分编码门槛，但没有降低工程判断门槛。不会验收的人，只会更快地产生更多待返工代码。

结语

回头看这轮 AI 编程演进，表面上是在从 Prompt 走向 Context、Tools、Agents 和 Workflows；更深层地看，是研发协作方式在被重新组织。AI 编程不再只是“模型帮我写一点代码”，而是在逐步变成“模型和系统一起完成一个任务”。

因此，理解今天的 AI 编程，不能只盯着模型，也不能只盯着流程。大模型决定它能走多远，harness 决定它能不能稳定到达。未来真正有竞争力的，不是单一意义上的更强模型，也不是脱离模型谈系统工程，而是把强模型更稳地嵌入真实开发流程的能力。说到底，工程世界最终奖励的从来不是“最会表演的工具”，而是“最能交付结果的工具”。

一句话总结

未来的竞争，不只是看谁的模型更强，而是看谁能把强模型放进一个更强的 harness 里。模型负责上限，harness 负责别翻车。
